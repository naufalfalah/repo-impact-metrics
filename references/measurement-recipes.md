# Measurement recipes

Exact commands for producing numbers that don't exist yet. Run what you can in the
sandbox; hand the rest to the user as a copy-paste block. Every measured number must be
recorded with: commit SHA, dataset/workload, machine, and the command used — this is
what the user will be asked about in an interview.

## Contents
1. Test coverage
2. Latency & throughput
3. LLM / agent evaluation harness
4. Container & build
5. Git ownership (works on private work repos, run locally)
6. What not to run

## 1. Test coverage

Coverage of the *critical module* is more persuasive than whole-repo coverage.

```bash
# Python
pip install pytest pytest-cov --break-system-packages
pytest --cov=app --cov-report=term-missing -q
pytest --cov=app/audit --cov-report=term -q        # one module

# JS/TS (Jest / Vitest)
npx jest --coverage --coverageReporters=text-summary
npx vitest run --coverage

# PHP (needs Xdebug or PCOV)
XDEBUG_MODE=coverage vendor/bin/phpunit --coverage-text
```

If tests need API keys or live cloud services, do not fake the keys. Report which tests
could not run and why, and give the user the command.

## 2. Latency & throughput

Bench the user's *own* service only. Start it locally (docker compose up / uvicorn),
then:

```bash
python3 scripts/latency_bench.py http://localhost:8000/health -n 300 -c 10
python3 scripts/latency_bench.py http://localhost:8000/api/x -X POST \
  -d @sample.json -H "Content-Type: application/json" -n 200 -c 10 --warmup 10
```

For a before/after claim: `git stash` or `git checkout <old-sha>`, rebuild, run the same
command, then return and re-run. Report both numbers and the delta. If the endpoint calls
a paid LLM, bench a small `-n` (≤30) and say so — LLM latency dominates and is not the
user's code.

Heavier tools if installed: `k6 run`, `hey -n 1000 -c 50`, `npx autocannon`.

## 3. LLM / agent evaluation harness

The highest-value measurement for AI projects. Minimal, honest structure:

```
evals/
  cases.jsonl        # {"id": ..., "input": ..., "expected": {...}} — 50–200 real cases
  run_eval.py        # runs the pipeline on each case, writes results.jsonl
  score.py           # compares to expected, prints metrics
```

Scoring guidance:
- **Extraction**: per-field exact match after normalization (dates → ISO, amounts →
  Decimal, trim whitespace). Report macro-average and the worst field.
- **Classification-like decisions** (verdict, escalate/approve): confusion matrix;
  report precision on the "dangerous" class (e.g. false auto-approve, false fraud flag).
- **Automation rate**: % of cases auto-handled; report *alongside* error rate among
  auto-handled cases — automation without its error rate is a vanity metric.
- **RAG retrieval**: hit@k for question→expected-source pairs.
- Record model version, temperature, prompt commit SHA. LLM outputs vary — run 3 times
  and report mean (and range if it's wide).

Label source must be defensible: real historical records (anonymized), a public dataset,
or labels from domain experts. Synthetic cases generated by the same LLM are not an eval —
say this if the user proposes it.

## 4. Container & build

```bash
docker build -t app:new . && docker images app:new --format '{{.Size}}'
git checkout <old-sha> && docker build -t app:old . && docker images app:old --format '{{.Size}}'
docker history app:new                                    # which layer is heavy
time docker build --no-cache -t app:new .                 # cold build time
gh run list --workflow=ci.yml --limit 20 --json durationMs 2>/dev/null   # CI durations
```

## 5. Git ownership — for work repos the user can't share

Give the user this block to run inside the company repo on their own machine. It prints
only aggregate numbers and paths, no source code, so it's typically safe to paste back —
but tell them to check their employer's policy and redact path names if needed.

```bash
python3 repo_metrics.py . --author "their@work-email" > ledger.md   # full ledger
git shortlog -sne --no-merges | head -15                            # who did what
git log --author="their@work-email" --no-merges --format= --name-only \
  | awk -F/ '{print $1"/"$2}' | sort | uniq -c | sort -rn | head -15
git log --author="their@work-email" --no-merges --format='%ad %s' --date=short | head -60
```

The commit-subject list is often the best memory aid: it surfaces the migrations,
incidents and refactors the user forgot they did. `repo_metrics.py` already buckets the
author's subjects by impact aspect ("Commit subjects by aspect"); the raw `git log` above
is for reading the full list when a bucket looks thin.

## 6. What not to run

- Anything needing production credentials, customer data, or the employer's network.
- Load tests against shared staging or any host the user does not control.
- Paid-API loops without the user's explicit OK on cost.
- `npm install` / `composer install` of huge trees just to count things — the ledger
  doesn't need dependencies installed. Install only to run tests.
